1. WHAT HAS BEEN DONE SO FAR?
------------------------------------------------------------------------
- Core Implementation: Built a complete Generative AI background replacement system using Stable Diffusion (Inpainting).
- LoRA Fine-Tuning: Trained two LoRA adapters on a fashion dataset. One is lightly trained (350 steps) for good generalization, and one is intentionally over-trained (44,000 steps) to showcase "Catastrophic Forgetting" (when the model forgets how to draw natural backgrounds and just zooms in on blurry fashion colors).
- Masking Architecture: We explicitly decouple generative hallucinations from the core product by using `rembg` (U²-Net) to calculate a deterministic alpha mask limit that Stable Diffusion cannot natively breach.
- MLOps Pipeline (Local): We containerized the tracking and inferencing. We use MLFlow to log the Hugging Face runs, and Prometheus/Grafana to map system vitals (GPU VRAM) and API health.
- Open-Source MLOps Philosophy: We intentionally rejected proprietary cloud AI services (like Vertex AI or SageMaker) in favor of a containerizable open-source stack. By relying solely on MLflow, Prometheus, and Grafana, our repository is infrastructure-agnostic and guarantees zero vendor lock-in.
- The Offline Pytest Suite: We implemented `tests/test_api.py`. This uses `pytest` and FastAPI's `TestClient` to mock out the heavy GPU Stable Diffusion logic, allowing us to perform rigorous CI/CD software engineering checks completely offline. Specifically, the suite tests 8 fast API components:
    1. Health Endpoint validation (`/health` correctly boots and returns `200 OK`).
    2. Payload integrity checks (Verifying `/generate` correctly throws a `422 Unprocessable` error if a generation request is sent without a valid image attachment).
    3. Model Parsing integrity (Verifying `/generate` correctly traps and denies inference if an unknown `model_mode` string is requested, guarding the backend against crashes).
    4. Input Extension Parsing (Verifying `/generate` gracefully rejects non-image byte-streams like `.pdf` uploads without crashing the PIL interpreter).
    5. Null Value Handling (Verifying `/generate` correctly blocks form submissions if the text prompt is entirely null or missing).
    6. Strict Type Casting (Verifying `/generate` correctly rejects numerical fields like steps passed as strings with a `422`).
    7. Sub-Endpoint Payload Enforcements (Verifying `/extract_mask` also correctly guards against payload drops).
    8. Environment Authentication Drops (Verifying `/upload` strictly throws a descriptive `400` instead of a server crash if the HuggingFace `HF_TOKEN` isn't injected).
- Evaluating Metrics (JSONL): We append CLIP Scores and Latency evaluations directly into `eval/eval_results.jsonl` upon every generated image.
- Automated MLOps Gating: We implemented `scripts/ops/register_adapter.py`. This strictly promotes LoRA adapters to production ONLY if their average CLIP score crosses the 22.0 threshold, effectively gating corrupt models programmatically!

4. PROBLEMS WE FACED & HOW WE SOLVED THEM (Good talking points for Viva!)
------------------------------------------------------------------------
Problem 1: MLflow CORS (Cross-Origin) Blocking UI Charts.
- Bug: When upgrading MLflow to v3.11, the dashboard started throwing "Internal Request Error" when attempting to query run histories through the Nginx reverse proxy.
- Fix: MLflow 3.x introduced strict security middleware that blocks cross-origin POST requests. We had to set the MLFLOW_SERVER_CORS_ALLOWED_ORIGINS environment variable and pass --allowed-hosts to explicitly whitelist our public IP (34.45.215.233) as a trusted origin.

Problem 2: GCP Firewall restricting Port accessibility.
- Bug: We deployed multiple services on separate ports (8000, 8501, 5000, 3000, 9090). Exposing all ports via GCP firewall rules is messy and insecure.
- Fix: We deployed an Nginx reverse proxy on port 80 that routes all traffic based on URL path (/api, /mlflow, /grafana, /prometheus). Only port 80 is exposed. Internal services communicate via localhost on the VM.

Problem 3: Catastrophic Forgetting via LoRA
- Bug/Phenomenon: While training the diffusion model on sneaker datasets, it began generating backgrounds that looked exactly like blurred white fabric rather than the mountains/deserts requested in the text prompt.
- Fix: By decreasing the steps from 44K to 350, we prevented the Unet from over-associating text prompt triggers with the local product colors. We left the 44K model in the project explicitly to map and demonstrate the dangers of Unet latency-drift.

Problem 4: Prometheus Docker Networking
- Bug: Prometheus inside a Docker container was scraping localhost:8000/metrics but getting "connection refused" because localhost inside Docker resolves to the container, not the host VM.
- Fix: Changed the target to 172.17.0.1:8000 (Docker bridge IP) so the container correctly reaches the FastAPI server running on the host.

5. THE "VENDOR LOCK-IN" TRICK
------------------------------------------------------------------------
If the instructor asks "Why did you use local MLflow and Prometheus instead of hooking natively into Google Cloud's Vertex AI metrics?"
- Answer: "We prioritize complete MLOps autonomy. By wiring the telemetry to open-source components that are natively bundled via docker-compose, this repository can be lifted from GCP and dropped onto AWS, Azure, or an on-prem cluster with zero code rewrites. We value zero-vendor lock-in."
